# Как подготовить проект к деплою на платформу

Инструкция для сайтов, которые разворачиваются под-сайтами: `<slug>.awwwdde.art`.
Всё написанное сверено с кодом `back/engine.py` и `back/caddy.py` — это не
рекомендации, а то, что платформа реально делает с проектом.

Коротко: проект должен быть **обычным веб-приложением в Docker, которое слушает
порт 8080 и отвечает 200 на `/healthz`**. Остальное платформа берёт на себя.

---

## 1. Обязательный контракт

Пять требований. Нарушение любого из них — деплой падает.

### 1.1. `Dockerfile` в корне репозитория

Контекст сборки — корень проекта, файл ищется по пути `<корень>/Dockerfile`.
Ни `docker/Dockerfile`, ни `Dockerfile.prod` не подойдут.

> `В <путь> нет Dockerfile — нарушен контракт гостя.`

### 1.2. Приложение слушает порт `8080` на `0.0.0.0`

Порт зашит в платформу (`GUEST_APP_PORT`), Caddy проксирует именно на него.
Слушать `127.0.0.1` нельзя: снаружи контейнера такой сокет не виден.

```dockerfile
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080"]
```

### 1.3. Есть эндпоинт `GET /healthz`, отвечающий 200

По нему платформа понимает, что приложение поднялось. Даётся 120 секунд.
Эндпоинт должен отвечать **без авторизации** и не ходить в тяжёлые внешние
сервисы — иначе на медленном старте деплой отвалится по таймауту.

```python
@app.get("/healthz")
def healthz():
    return {"status": "ok"}
```

### 1.4. В образе есть `wget` или `curl`

**Самая частая причина непонятного падения.** Healthcheck выполняется не
снаружи, а **внутри контейнера** командой:

```sh
wget -qO- http://localhost:8080/healthz || curl -fsS http://localhost:8080/healthz
```

Если в образе нет ни того, ни другого, приложение может работать идеально —
деплой всё равно упадёт с таймаутом. Проверено на популярных базах:

| Базовый образ | wget | curl |
|---|---|---|
| `python:3.12-alpine` | есть | нет |
| `node:20-alpine` | есть | нет |
| `nginx:alpine` | есть | есть |
| `python:3.12-slim` | **нет** | **нет** |
| `node:20-slim` | **нет** | **нет** |

На alpine ничего делать не нужно — `wget` там из busybox. На debian-slim
добавьте одну строку:

```dockerfile
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*
```

### 1.5. Никакого состояния в файловой системе контейнера

App-контейнер **пересоздаётся начисто при каждом деплое**. Загруженные
пользователями файлы, SQLite-база, кэш на диске — всё это исчезнет.
Переживает деплой только Postgres (см. ниже).

## 2. Что платформа даёт сама

Ничего из этого настраивать не нужно, оно приезжает готовым.

### Переменные окружения

| Переменная | Что внутри |
|---|---|
| `DATABASE_URL` | `postgresql://<slug>:<пароль>@<slug>_db:5432/<slug>` |
| `PUBLIC_SITE_URL` | `https://<slug>.awwwdde.art` |
| `SECRET_KEY` | случайный, **стабильный между деплоями** |
| `JWT_SECRET` | случайный, стабильный между деплоями |

Стабильность важна: сессии и подписанные токены не протухают при передеплое.

Свои переменные добавляются в панели (карточка стенда → `.env`). Они
прокидываются **поверх** этих четырёх, то есть при желании их можно
переопределить — например, зафиксировать свой `PUBLIC_SITE_URL`.

Читайте переменные из окружения, а не из файла `.env` в образе: файла там нет.

### База данных

Postgres 16 поднимается автоматически, отдельным контейнером на проект:

- пользователь, база и владелец — всё называется как slug проекта;
- данные лежат в volume `<slug>_db_data` и **переживают** и передеплой,
  и удаление проекта без галки «снести с данными»;
- платформа ждёт готовности базы (`pg_isready`) до старта приложения, так что
  на первом запросе она уже принимает соединения.

Миграции — забота проекта. Гоняйте их на старте контейнера:

```dockerfile
CMD sh -c "alembic upgrade head && uvicorn main:app --host 0.0.0.0 --port 8080"
```

### Домен и HTTPS

Поддомен `<slug>.awwwdde.art` и сертификат к нему выпускаются сами.
Кастомные домены добавляются в панели; сертификат выпустится, когда домен
начнёт резолвиться на сервер.

**Приложение отдаёт обычный HTTP.** TLS терминирует Caddy. Не включайте
принудительный редирект на https внутри приложения — получите цикл.

Заголовки `X-Forwarded-Proto` и `X-Forwarded-For` приходят от прокси; если
фреймворк умеет им доверять, включите (`--proxy-headers` у uvicorn,
`trust proxy` у express).

## 3. Откуда берётся код

Три варианта, задаются полем `source` при создании стенда:

| `source` | Что происходит |
|---|---|
| git-URL (`https://…`, `git@…`, `…​.git`) | `git clone --depth 1`, при следующих деплоях `git pull --ff-only` |
| путь к папке | содержимое копируется в `workspaces/<slug>` |
| пусто | ожидается, что код уже лежит в `workspaces/<slug>` |

Приватный репозиторий по https потребует токена в URL. Проще положить код
папкой или использовать публичное зеркало.

При копировании папки **не переносятся**: `.git`, `node_modules`, `dist`,
`__pycache__`, `*.db`, `backups`. Если проект без них не собирается — это
проблема проекта, сборка должна восстанавливать зависимости сама.

`git pull --ff-only` означает, что ветка с переписанной историей (force-push,
rebase) обновиться не сможет. Тогда проще удалить стенд и создать заново.

## 4. Готовые примеры

### FastAPI / Python

```dockerfile
FROM python:3.12-slim

# curl нужен платформе для healthcheck — без него деплой падает по таймауту.
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

# Логи должны идти в stdout без буфера, иначе их не видно в панели.
ENV PYTHONUNBUFFERED=1

EXPOSE 8080
CMD ["uvicorn", "main:app", "--host", "0.0.0.0", "--port", "8080", "--proxy-headers"]
```

### Next.js

```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:20-alpine AS runner
WORKDIR /app
ENV NODE_ENV=production
# Платформа даёт только 8080; Next по умолчанию слушает 3000.
ENV PORT=8080
ENV HOSTNAME=0.0.0.0

# standalone-сборка: next.config.ts -> output: 'standalone'
COPY --from=builder /app/.next/standalone ./
COPY --from=builder /app/.next/static ./.next/static
COPY --from=builder /app/public ./public

EXPOSE 8080
CMD ["node", "server.js"]
```

`/healthz` в App Router:

```ts
// app/healthz/route.ts
export function GET() {
  return Response.json({ status: 'ok' })
}
```

### Статика на nginx

```dockerfile
FROM node:20-alpine AS builder
WORKDIR /app
COPY package.json package-lock.json* ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:alpine
COPY --from=builder /app/dist /usr/share/nginx/html
COPY nginx.conf /etc/nginx/conf.d/default.conf
EXPOSE 8080
```

```nginx
# nginx.conf
server {
    listen 8080;
    root /usr/share/nginx/html;

    # Healthcheck платформы. Без него деплой не пройдёт.
    location = /healthz {
        add_header Content-Type application/json;
        return 200 '{"status":"ok"}';
    }

    location / {
        try_files $uri $uri/ /index.html;
    }
}
```

## 5. Чеклист перед деплоем

Проверяется локально одной командой — если так проект поднимается, поднимется
и на платформе:

```bash
docker build -t check .
docker run --rm -p 8080:8080 -e DATABASE_URL=postgresql://... check
```

- [ ] `Dockerfile` лежит в корне репозитория
- [ ] приложение слушает `0.0.0.0:8080`
- [ ] `curl http://localhost:8080/healthz` отдаёт 200
- [ ] `docker run --rm --entrypoint sh check -c 'command -v wget || command -v curl'` что-то печатает
- [ ] конфигурация читается из переменных окружения, а не из файла
- [ ] `DATABASE_URL` используется как есть, хост не захардкожен
- [ ] ничего не пишется на диск контейнера в расчёте на сохранность
- [ ] нет принудительного редиректа на https внутри приложения
- [ ] нет `ports:`/`expose` на других портах в расчёте на доступ снаружи

## 6. Что означают ошибки деплоя

| Сообщение | Причина |
|---|---|
| `В … нет Dockerfile — нарушен контракт гостя` | Dockerfile не в корне или репозиторий пустой |
| `docker build упал: …` | Обычная ошибка сборки, читайте текст ниже |
| `app-контейнер упал на старте` | Процесс завершился; в сообщение подставлены последние 40 строк логов |
| `app … не прошёл healthcheck за 120с` | Три варианта: слушает не 8080, нет `/healthz`, либо в образе нет `wget` и `curl` |
| `Postgres … не поднялся за 60с` | Занят volume или диск переполнен; смотрите логи `<slug>_db` |
| `Исходники не найдены` | Неверный git-URL или пустая папка `workspaces/<slug>` |

Логи приложения — в панели, карточка стенда → «Логи». Если контейнер упал,
последние строки уже подставлены в текст ошибки.

---

## 7. Чего платформа не делает

Чтобы не искать несуществующие настройки:

- **не пробрасывает порты на хост** — снаружи проект доступен только через
  Caddy по своему домену;
- **не хранит файлы** — нужен объектный сторадж, подключайте S3-совместимый;
- **не запускает фоновые воркеры** — на проект ровно два контейнера,
  приложение и база. Celery, cron и очереди поднимайте внутри своего образа
  (например, супервизором) либо выносите наружу;
- **не бэкапит гостевые базы** — пока это на стороне проекта;
- **не собирает несколько сервисов из одного репозитория** —
  `docker-compose.yml` в репозитории гостя игнорируется, собирается ровно
  один `Dockerfile`.

## 8. Нагрузка

После деплоя платформа снимает с обоих контейнеров стенда CPU, память, сеть и
диск раз в 15 секунд. Смотреть — в панели, карточка стенда → нагрузка.

Чтобы цифры были осмысленными:

- не крутите busy-loop в фоне: он покажет постоянные 100% CPU и утопит
  реальные всплески;
- если контейнер циклически перезапускается, это видно по счётчику рестартов
  раньше, чем по графику нагрузки;
- аптайм считается по доле замеров, в которых приложение было живо, поэтому
  короткое падение между замерами может остаться незамеченным. Для точного
  учёта смотрите события в той же карточке.
