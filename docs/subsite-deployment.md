# Настройки выкладки подсайтов

В `/admin/projects` у каждого сайта есть кнопка **Выкладка**. Она открывает настройки, предварительную проверку и последние 30 попыток. Новый сайт сначала создаётся, затем настраивается; сборка запускается отдельно.

## Что настраивается

- Источник и ветка Git. Пустая ветка означает HEAD репозитория; при обновлении явно выполняются fetch и checkout выбранной версии. Локальные несохранённые изменения Git не сбрасываются принудительно.
- Контекст сборки и Dockerfile относительно контекста. `..`, абсолютные пути и выход через символические ссылки запрещены.
- Docker-кэш и обновление базового образа.
- Порт приложения; пустое значение сохраняет общий порт панели. Явно заданный порт также передаётся приложению как `PORT`.
- Команда запуска в виде JSON-массива аргументов; `[]` оставляет CMD из Dockerfile. Автоматической оболочки нет.
- HTTP-путь, ожидаемый код ответа, время ожидания и интервал проверки. Образ должен содержать curl или wget. Редирект больше не принимается за успешный HTTP 200.
- Лимиты памяти, CPU и процессов контейнера приложения; пустые значения сохраняют прежнее поведение без лимитов.
- Политика перезапуска и использование управляемого PostgreSQL. Отключение БД не удаляет прежний контейнер/volume. Можно передать внешний DATABASE_URL через существующий редактор переменных.
- Ротация журнала приложения: до трёх файлов по 10 МБ.

Профили Node/Next и статики заполняют типовые значения, но не генерируют Dockerfile. Dockerfile приложения должен поддерживать выбранный порт и способ запуска. Ресурсные лимиты относятся к приложению, а не к Docker build или PostgreSQL.

Сохранение настроек не перезапускает сайт. Активная конфигурация сохраняется отдельно после успешного деплоя: изменение порта в форме не меняет маршрут текущего сайта. Start, дополнительные домены и восстановление маршрутов Caddy используют активный порт.

## Проверка и история

Предварительная проверка не получает Git-код, не запускает Docker и не проверяет внешние зависимости. Она проверяет сохранённую конфигурацию и уже доступные файлы; явно сообщает, что будет проверено только при деплое. Ошибка проверки блокирует запуск из открытого окна до исправления; сервер всё равно проверяет контракт независимо от UI.

Каждая попытка сохраняется в `deployments`: начало/окончание, статус, текущий этап, commit SHA для Git и ошибка. Этапы: очередь → исходники → сборка → PostgreSQL → контейнер → HTTP → маршрут → готово. История в окне обновляется раз в 3 секунды. Ошибки очищаются от известных значений секретов и паролей в URL.

Атомарный захват состояния проекта отклоняет второй деплой с 409. Редактирование конфигурации и доменов, start/stop и удаление блокируются на время выкладки. Копирование локальной папки сначала выполняется в промежуточный каталог: ошибка копирования сохраняет старый workspace. Пути очистки проверяются относительно каталога workspaces.

## API и обновление

- `PUT /api/projects/{slug}/settings` — имя, источник и `deploy_config`.
- `GET /api/projects/{slug}/preflight` — предварительная проверка.
- `GET /api/projects/{slug}/deployments` — последние 30 попыток.
- `POST /api/projects/{slug}/deploy` — **202 Accepted**, задание уже сохранено; это не ответ о готовом сайте. История возвращает id и этап задания. CLI обновлён на 202.
- Прежние create/start/stop/logs/domain-эндпоинты сохранены, все административные маршруты требуют авторизации.

Нужны обновлённые frontend и backend. `init_db()` при штатном старте добавляет `projects.deploy_config`, `projects.active_config` и таблицу `deployments` с `request_config`; здесь миграция реальной БД не запускалась. Старые настройки по умолчанию: общий порт панели, `/healthz`, 120 секунд, PostgreSQL, Dockerfile в корне, CMD образа и прежняя политика restart.

## Фоновая очередь и переключение версии

`deploy_worker` — отдельный Compose-сервис. Панель сохраняет задание и снимок source, DeployOptions и **зашифрованных** env в одной транзакции с блокировкой проекта. Секретный снимок не включён в API истории. Позднейшие правки env применятся к следующему заданию.

Worker обрабатывает один релиз за раз. PostgreSQL session advisory lock не позволяет двум worker одновременно исполнять очередь. При потере соединения блокировки дальнейшие этапы прекращаются. Закрытие браузера и перезапуск HTTP-панели не прерывают worker. После перезапуска worker незавершённый этап до публикации повторяется с тем же id. Git-ветка при таком повторе может уже содержать новый commit: окончательный SHA фиксируется в истории. Произвольные действия приложения на старте должны быть идемпотентными.

Новый образ получает `awwwdde/<slug>:release-<id>`, контейнер — `<slug>_release_<id>`. Рабочий контейнер не удаляется при сборке и проверке нового. Только после успешной HTTP-проверки Caddy заменяет маршрут целиком; затем панель фиксирует активные имя, образ и конфигурацию. Логи, метрики, start/stop, дополнительные домены и восстановление маршрутов используют активное имя, включая прежние `<slug>_app`.

Если ответ Caddy потерян или фиксация публикации не удалась, обе версии сохраняются. Задание остаётся на этапе «Публикация» с ошибкой; worker повторяет проверку и публикацию **без пересборки или удаления кандидата**. Другие задания без ошибки имеют приоритет перед повтором. Это может потребовать устранения причины недоступности Caddy оператором; отмены из UI пока нет.

Через 60 секунд после успешной публикации worker удаляет предыдущий контейнер и его release-образ без force для образа; не трогает активный контейнер. Это ограниченный период для завершения старых запросов, не обещание бесконечного сохранения WebSocket/долгих соединений. Неудачные кандидаты также очищаются; при недоступном Docker очистка повторяется позже. Старые legacy-образы `latest` автоматически не удаляются. При удалении проекта удаляются его release-контейнеры и образы из истории.

Сбой сборки или HTTP-проверки завершает попытку с ошибкой; предыдущая активная версия и её конфигурация сохраняются. Это не откат пользовательских БД: обе версии временно используют одну БД. **Миграции обязаны быть обратно совместимыми**, а фоновые задачи приложения — учитывать одновременный запуск двух контейнеров. Автоматический rollback БД, кнопка возврата релиза, SSE-транспорт и проверка публичного HTTPS после переключения пока не реализованы.

Старые незавершённые синхронные попытки без снимка помечаются ошибкой, поскольку безопасно повторить их нельзя. Новую попытку запускает оператор после проверки состояния.

## Как включить на сервере

После обновления исходников:

```sh
docker compose up -d --build panel deploy_worker
```

Новый worker ждёт успешный healthcheck панели; панель выполняет идемпотентную миграцию. У обеих служб должны совпадать DATABASE_URL, ENV_ENCRYPTION_KEY, Docker-сеть и volume workspaces. Отдельный worker не запускает сидирование сайта. При запуске без Compose сначала запустить обновлённую панель, затем из `back/` выполнить `python deploy_worker.py` с тем же окружением. Без worker задания остаются в очереди.

Существующий worker при обновлении нужно остановить **до** запуска миграции новой панелью: не допускайте одновременную работу старого и нового кода. Перед первой выкладкой платформы нужна проверка на отдельном тестовом подсайте. Здесь миграция сервера и реальные выкладки не выполнялись.

## Проверки

18 backend-тестов: сохранение задания без вызова Docker из HTTP, повторный запрос 409, запрет редактирования, снимок env без выдачи его в историю, отдельный release-тег и контейнер, сохранение предыдущего при failed health, восстановление прерванного этапа, повтор публикации без пересборки, очистка после grace period, потеря worker-блокировки, маскирование секретов, активный порт/контейнер, отсутствие удаления маршрута перед заменой и отказ от создания дубля при ошибке Caddy.

Используются одноразовая SQLite, тестовый клиент FastAPI и заглушки Docker/Caddy/соединения advisory lock. ESLint, TypeScript и `docker compose config --quiet` проверяются отдельно. Реальные PostgreSQL advisory locks, Docker и Caddy в этом окружении сквозным тестом не проверены: Docker Engine не запущен. Фронтенд сохраняет текущий UI; изменены подписи очереди и поведения выкладки.

## Консоль и нагрузка — обновление

В карточке подсайта есть **Консоль** и отдельные **Логи приложения**. Консоль доступна до публикации, во время сборки и после неудачной выкладки. После постановки в очередь она открывается автоматически. Можно выбрать одну из 30 последних попыток, отключить автопрокрутку и скачать `.log`. Рядом с действиями карточки и на дашборде — прямая HTTPS-ссылка на сайт; до первой успешной выкладки доступность адреса не гарантируется.

`DeploymentLog` хранит этап, уровень, время и текст. Начальная запись создаётся в той же транзакции, что задание. Worker сохраняет этапы, вывод Git (по завершении команды), поток Docker build, проверки готовности и startup-вывод кандидата. Перед удалением неудачного контейнера сохраняется хвост его журнала. После первой публикации обычный runtime-вывод по-прежнему смотрят через «Логи приложения». Консоль — просмотр, не shell. Она не обнаруживает автоматически все баги и не заменяет тесты приложения.

`GET /api/projects/{slug}/deployments/{id}/logs?after=0&limit=200` — авторизованный вывод с курсором; максимум 500 записей в ответе, доступ только к попытке указанного проекта. Интерфейс запрашивает новые строки раз в 2 секунды, при скрытой вкладке останавливает обновление. История и строки остаются после закрытия страницы. Журнал ограничен 5000 строками плюс уведомление о лимите; длинные строки обрезаются, ANSI-последовательности удаляются, известные env/базовые секреты и типовые присваивания token/password скрываются. Фрагменты Docker-потока соединяются до маскирования. Старые попытки подробного вывода не имеют.

При старте обновлённой панели `init_db()` создаёт `deployment_logs` и добавляет nullable `metric_samples.state`. Старые замеры остаются совместимыми: для них аптайм использует прежнюю оценку по памяти, новые — фактическое состояние контейнера.

Исправлена воспроизведённая ошибка SQLAlchemy: `Row.t` возвращал всю строку вместо колонки даты и ломал сериализацию графиков HTTP 500. Теперь raw/hourly читают `row._mapping['t']`. Ошибка обращения к Docker при чтении размера БД не ломает сведения о сайте: возвращаются доступные данные и предупреждение.

Графики и дашборд обновляются раз в 15 секунд. Отсутствие свежего app-замера больше 90 секунд отмечается явно; устаревшие итоговые CPU/RAM не выдаются за текущие и не подменяются нулями. При доступном Docker отсутствие контейнера записывается как `missing`, что учитывается в аптайме. Отключённая управляемая БД не опрашивается. Сборщик использует активное release-имя.

Добавлены регрессионные проверки всех четырёх периодов, сериализации настоящих SQLAlchemy Row, missing/stale данных, частичной недоступности Docker, раздельного активного имени и сохранения/маскирования/пагинации консоли. SQLite заменяет только PostgreSQL date_bin при тесте SQL-группировки; реальный PostgreSQL и Docker здесь не запускались. Визуальная проверка новой консоли не подтверждена: браузер заблокировал локальный тестовый URL (`ERR_BLOCKED_BY_CLIENT`). Изолированный proxy остановлен после проверки доступности.

## Страница подсайта и диагностика сервера

`/admin/projects/:slug` — отдельная страница с адресом, состоянием, активным release-образом, контейнером и датой публикации. Разделы сохраняются в URL (`?tab=console`, `load`, `diagnostics`, `settings`). Доступны нагрузка, консоль и существующие редакторы параметров, доменов, env и runtime-логов. Список проектов и дашборд ссылаются на эту страницу. Состояние проекта обновляется раз в 5 секунд, нагрузка — раз в 15; при скрытой вкладке запросы приостановлены.

`GET /api/system/diagnostics` требует авторизации и возвращает независимые проверки Docker API, heartbeat worker, Caddy Admin API, свободного места и прав на файловой системе workspaces. При доступном Docker клиент закрывается после запроса. Таймаут соединения Docker — 3 секунды; Caddy использует существующий ограниченный ping. Проверка диска не отражает свободное место в отдельном хранилище Docker-образов. Меньше 1 ГБ — ошибка, меньше 5 ГБ — предупреждение; успешная проверка не гарантирует достаточное место для конкретной сборки.

Worker в отдельном потоке обновляет `service_heartbeats` каждые 10 секунд, в том числе во время длительной сборки. Запись старше 45 секунд или отсутствие записи — ошибка диагностики. Heartbeat подтверждает живой процесс и запись в БД, но не прогресс сборки или отсутствие зависшего Docker-запроса. Таблица создаётся через `init_db()` при старте обновлённой панели; затем нужно перезапустить worker.

`GET /api/projects/{slug}/readiness` объединяет серверную диагностику, существующую проверку файлов и read-only `git ls-remote` выбранной ветки. Таймаут Git — 12 секунд, интерактивные запросы credentials отключены; для SSH обязательна проверка известных host keys. Исходники не скачиваются, контейнеры не запускаются, секреты и stderr не выдаются. Доступ Git проверяется из HTTP-панели: worker должен иметь то же окружение и SSH-credentials.

Кнопка «Развернуть» на отдельной странице и в окне выкладки выполняет диагностику перед постановкой задания в очередь. В списке сначала открывается окно настроек и проверки; после редактирования env можно перейти туда же. Ошибки блокируют этот UI-запуск, предупреждения — нет. Диагностика не является транзакционной гарантией: состояние сервера может измениться после проверки. Прямой POST API и CLI по-прежнему могут поставить задание без предварительной диагностики — ошибки сохранятся в консоли worker.

19 backend-тестов включают авторизацию диагностических маршрутов, свежий/отсутствующий/просроченный heartbeat, недоступные Docker и Caddy, нехватку диска, безопасную проверку Git и объединение результата с проектным preflight. Для включения нового поведения обновить панель, frontend и worker. Реальный Docker Engine на этой машине недоступен; сквозной деплой и визуальная проверка этой страницы не подтверждены.
